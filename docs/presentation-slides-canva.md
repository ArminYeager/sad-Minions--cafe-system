### สไลด์ที่ 2: ปัญหาเดิม vs วิธีแก้ใหม่ (As-Is vs To-Be) (1 นาที)
* **เลย์เอาต์บน Canva:** แบ่ง 2 คอลัมน์ (เปรียบเทียบซ้าย-ขวา) 
  * ด้านซ้าย (สีเทา/แดงอ่อน): ❌ As-Is จดกระดาษ คอขวด ผิดพลาด
  * ด้านขวา (สีทอง/เขียวอ่อน): ✅ To-Be ระบบดิจิทัล Real-time POS
* **รูปภาพประกอบ:** ดึงภาพจาก `docs/images/As-Is.jpg` และ `docs/images/to-be.png` มาวางเทียบกัน
* **ข้อความบนสไลด์:**
  * **ปัญหาเดิม (As-Is Pain Points):**
    * ⚠️ จดออเดอร์ด้วยมือ ผิดพลาดเฉลี่ย 3–5 แก้ว/วัน ช่วงเร่งด่วน
    * ⚠️ คิดเงินล่าช้า เกิดคิวสะสมหน้าร้าน
    * ⚠️ สต็อกนมสดและเมล็ดกาแฟหมดกะทันหัน เสียโอกาสการขาย
    * ⚠️ เจ้าของร้านไม่รู้ยอดขายสด ต้องรอปิดกะนับบิลกระดาษ
  * **กระบวนการใหม่ (To-Be Transformation):**
    * ✨ แตะสั่งซื้อหน้าร้าน คำนวณเงินสดทันที ออกใบเสร็จรวดเร็ว
    * ✨ ตัดสต็อกวัตถุดิบอัตโนมัติทันทีที่มีการขาย (Real-time Deduction)
    * ✨ แจ้งเตือนสินค้าใกล้หมด (Low Stock Alert < 10 ชิ้น) ป้องกันของขาด
    * ✨ Real-time Sales Dashboard ดูยอดขายและเมนูขายดีได้ทันทีทุกสาขา
* **บทพูดนำเสนอ (จตุพร - 50 วินาที):**
  > "จากการศึกษาความเป็นไปได้ (Feasibility Study) และสำรวจกระบวนการทำงานแบบเดิม (As-Is) ของ Minions Cafe เราพบว่าปัญหาคอขวดหลักเกิดจากการจดออเดอร์ลงกระดาษและใช้เครื่องคิดเลข ทำให้คิดเงินผิดและออเดอร์ตกหล่นในชั่วโมงเร่งด่วน อีกทั้งสต็อกวัตถุดิบหมดโดยไม่รู้ตัวล่วงหน้า กลุ่มเราจึงออกแบบกระบวนการใหม่ (To-Be) ด้วยระบบ POS ที่แตะสั่งง่าย คำนวณราคารวดเร็ว ตัดสต็อกและเตือนวัตถุดิบใกล้หมดแบบอัตโนมัติ พร้อมส่งข้อมูลยอดขายตรงสู่หน้าจอผู้บริหารทันทีค่ะ"

### สไลด์ที่ 4: การออกแบบสถาปัตยกรรมและฐานข้อมูล (1 นาที)
* **เลย์เอาต์บน Canva:** วาง 3 กล่องภาพแบบ Grid 
  * กล่อง 1: Class Diagram (`docs/wk06-class-diagram.png`)

  * กล่อง 3: 3-Tier Web Architecture (`docs/images/wk11-development-view.png`)
* **ข้อความบนสไลด์:**
  * **โครงสร้างระบบ (3-Tier Clean Architecture):**
    * **Presentation Tier:** HTML5, Modern CSS, Responsive SPA Interface
    * **Application Tier:** Node.js, Express RESTful API, OOP Controllers & Models

    * `Branch` 1:N `Employee` & `Order` (รองรับหลายสาขา)

  > "ในส่วนของการออกแบบเชิงเทคนิค เรายึดหลัก Object-Oriented และ Clean Architecture โดยแบ่งระบบออกเป็น 3-Tier อย่างชัดเจน ฝั่งหน้าบ้านเชื่อมต่อกับ Backend ผ่าน RESTful API ที่มีโครงสร้างโมเดล Menu, Order, และ Branch ตรงตาม Class Diagram และ ER Diagram ที่เราวางไว้ ทำให้ระบบรองรับการขยายสาขา (Multi-branch) ในอนาคตได้อย่างยืดหยุ่นและปลอดภัยค่ะ"

### สไลด์ที่ 6: ผลการทดสอบการใช้งานจริง (Usability Testing) (0.5 นาที)
* **เลย์เอาต์บน Canva:** กราฟวงกลมหรือตัวเลขสถิติขนาดใหญ่ เด่นสะดุดตา
* **ข้อความบนสไลด์:**
  * 🎯 **ผลลัพธ์การทดสอบระบบ (SUS Score: 82.5 / 100 - Grade A / Excellent):**
    * ⏱️ **ความเร็วในการสั่งออเดอร์:** ใช้เวลาเฉลี่ยเพียง 12 วินาที/ออเดอร์ (เร็วกว่าเดิม 65%)
    * 🛡️ **ความแม่นยำ (Error Rate):** 0% ความผิดพลาดในการคิดเงินและตัดสต็อก
    * 💡 **การปรับปรุงตามฟีดแบ็ก (Sprint Feedback Loop):**
      * เพิ่มปุ่มล้างรายการและปรับจำนวนในตะกร้าได้ง่ายขึ้น (FR-09)
      * ปิดปุ่มสั่งสำหรับเมนูที่หมดสต็อก พร้อมแสดงป้าย 'หมด' ชัดเจน (FR-11)
      * เพิ่มหน้าต่างแจ้งเตือนวัตถุดิบวิกฤต (Low Stock Alert)
* **บทพูดนำเสนอ (ชนิดาภา - 35 วินาที):**
  > "จากการนำระบบไปทดสอบการใช้งาน (Usability Testing) กับกลุ่มตัวอย่างพนักงานและผู้ใช้จริง พบว่าได้คะแนน System Usability Scale สูงถึง 82.5 คะแนน ซึ่งอยู่ในระดับยอดเยี่ยม (Grade A) พนักงานสามารถทำรายการได้เสร็จสิ้นภายใน 12 วินาที และความผิดพลาดในการทอนเงินเป็นศูนย์ นอกจากนี้เรายังได้นำ Feedback ในแต่ละสัปดาห์มาปรับระบบให้ตอบโจทย์ผู้ใช้ยิ่งขึ้น เช่น การบล็อกเมนูที่หมดสต็อกทันทีค่ะ"

# 🎯 แนวทางเตรียมตอบคำถามอาจารย์ (Anticipated Q&A Guide)

1. **อาจารย์ถาม:** *"ถ้าร้านมีสาขาเพิ่มเป็น 10 สาขา ระบบจะจัดการเรื่องสต็อกและรายงานอย่างไร?"*
   * **ผู้ตอบ (มนทกานต์):** *"ระบบออกแบบฐานข้อมูลให้มีฟิลด์ `branch_id` กำกับทั้งในตารางสต็อกและออเดอร์ ทำให้ระบบสามารถแยกดูยอดขายและสต็อกรายสาขาได้ทันที หรือรวมเป็น Dashboard ส่วนกลางของเจ้าของร้านได้โดยไม่ต้องแก้โครงสร้างตารางค่ะ"*
2. **อาจารย์ถาม:** *"มีการจัดการความปลอดภัยอย่างไรกับข้อมูลยอดขายและการตัดสต็อก?"*
   * **ผู้ตอบ (ชาลิสา/บุษชยาภา):** *"ระบบมีการแยกบทบาท (Role-based access) พนักงานแคชเชียร์จะเข้าถึงได้เฉพาะหน้า POS เพื่อขายสินค้าเท่านั้น ขณะที่หน้าจัดการสต็อกและการดูรายงานยอดขายจำเป็นต้องมีสิทธิ์ของผู้จัดการหรือเจ้าของร้านค่ะ"*
3. **อาจารย์ถาม:** *"ทำไมถึงเลือกใช้ Node.js และ Vanilla JavaScript แทนการใช้ Framework สำเร็จรูปขนาดใหญ่?"*
   * **ผู้ตอบ (มนทกานต์):** *"เนื่องจากระบบ POS หน้าร้านต้องการความเร็วในการตอบสนองสูงสุด (Low Latency) และไม่ต้องการความซับซ้อนของ Bundle Size การใช้ Vanilla JS และ Express API ช่วยให้โหลดหน้าจอได้เร็วกว่า 0.5 วินาที และบำรุงรักษาง่ายตามโจทย์ของร้านกาแฟขนาดกลางค่ะ"*
