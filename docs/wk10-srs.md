## 1. บทนำ (Introduction)

### 1.1 วัตถุประสงค์ของเอกสาร (Purpose)
เอกสารข้อกำหนดความต้องการซอฟต์แวร์ (SRS) ฉบับนี้จัดทำขึ้นเพื่อรวบรวมและระบุข้อกำหนดความต้องการทั้งหมดของระบบ Minions Cafe ทั้งด้านหน้าที่การทำงาน (Functional Requirements), ด้านคุณลักษณะระบบ (Non-Functional Requirements), และข้อจำกัดเชิงเทคนิค (Constraints) เพื่อใช้เป็นเกณฑ์อ้างอิงในการออกแบบสถาปัตยกรรม การพัฒนาโค้ด และการทดสอบระบบ

### 1.2 ขอบเขตของโครงการ (Project Scope)
ระบบ Minions Cafe เป็นระบบบริหารจัดการร้านกาแฟแบบหลายสาขา (Multi-branch) ครอบคลุมฟังก์ชันการทำงานหลัก ได้แก่:
1. ระบบขายหน้าร้าน (Point of Sale - POS) สำหรับรับออเดอร์ คำนวณราคา และออกใบเสร็จ
2. ระบบจัดการเมนูและหมวดหมู่สินค้า (Menu Management) พร้อมการแจ้งเตือนสต็อกต่ำ
3. ระบบตัดสต็อกอัตโนมัติ (Inventory & Stock Movement)
4. ระบบรายงานสรุปยอดขาย (Sales Reporting) แบบ On-demand สำหรับเจ้าของร้าน
5. การรองรับการเลือกสาขา (Branch Selection) ในทุกหน้าจอ

## 3. ข้อกำหนดความต้องการเชิงหน้าที่ (Functional Requirements)

### 3.1 ระบบขายหน้าร้าน (POS)
- **FR-01:** ระบบต้องแสดงรายการเมนูตามสาขาที่เลือก โดยแบ่งตามหมวดหมู่ (กาแฟ, ชา, ขนม) พร้อมราคาและจำนวนสต็อกคงเหลือ
- **FR-02:** ระบบต้องให้ผู้ใช้เลือกสินค้าและระบุจำนวนเข้าสู่ตะกร้าสินค้าได้
- **FR-03:** ระบบต้องคำนวณราคารวมของแต่ละรายการและยอดรวมทั้งสิ้นแบบเรียลไทม์ทันทีที่มีการเปลี่ยนแปลง
- **FR-04:** ระบบต้องรองรับการเลือกวิธีชำระเงิน (เงินสด หรือ QR Code พร้อมเพย์)
- **FR-05:** ระบบต้องออกใบเสร็จรับเงินดิจิทัลทันทีหลังยืนยันการชำระเงิน พร้อมระบุหมายเลขออเดอร์ วันเวลา สาขา พนักงาน และรายการสินค้า
- **FR-06:** ระบบต้องปิดการใช้งานปุ่มยืนยันออเดอร์หากไม่มีรายการสินค้าในตะกร้า หรือยังไม่ได้เลือกวิธีชำระเงิน (Error Prevention)

### 3.2 ระบบจัดการสต็อกและเมนู (Inventory & Menu)
- **FR-07:** ระบบต้องตัดสต็อกสินค้าในฐานข้อมูลทันทีเมื่อมีการยืนยันออเดอร์
- **FR-08:** ระบบต้องแสดงสัญลักษณ์แจ้งเตือน "ต่ำกว่าเกณฑ์" (Low Stock) เมื่อสต็อกเหลือน้อยกว่า 10 หน่วย
- **FR-09:** ระบบต้องปฏิเสธการสั่งซื้อหากจำนวนสินค้าในคำสั่งซื้อมากกว่าสต็อกคงเหลือ
- **FR-10:** ระบบต้องปิดการใช้งานปุ่ม '+ เพิ่ม' และแสดงสถานะ 'หมด' สำหรับเมนูที่ `stock_quantity = 0` (FR-11 จาก feedback สัปดาห์ที่ 13)
- **FR-11:** ระบบต้องรองรับการเพิ่ม แก้ไขราคา ปรับจำนวนสต็อก และลบรายการเมนูของสาขาที่เลือก

### 3.3 ระบบรายงานยอดขาย (Sales Reporting)
- **FR-12:** ระบบต้องสรุปยอดขายรวม (Total Revenue) และจำนวนออเดอร์ทั้งหมด (Total Orders) ตามช่วงเวลาและสาขาที่เลือก
- **FR-13:** ระบบต้องจัดอันดับเมนูขายดี (Best Seller) โดยระบุชื่อเมนูและจำนวนที่จำหน่ายได้
- **FR-14:** ระบบต้องอัปเดตรายงานยอดขายทันทีเมื่อมีออเดอร์ใหม่เกิดขึ้นในระบบ (Real-time consistency)
- **FR-15:** ระบบต้องรองรับการกรองข้อมูลแยกรายสาขา และเปรียบเทียบยอดขายระหว่างสาขาได้

## 4. ข้อกำหนดที่ไม่ใช่เชิงหน้าที่ (Non-Functional Requirements)

### 4.1 ประสิทธิภาพ (Performance)
- **NFR-01 (Response Time):** การคำนวณยอดเงินในหน้า POS ต้องแสดงผลทันที (ไม่เกิน 100 มิลลิวินาที) เมื่อผู้ใช้กดเพิ่มหรือลดจำนวนสินค้า
- **NFR-02 (Throughput):** API ฝั่ง Backend ต้องประมวลผลคำขอยืนยันออเดอร์ (`POST /api/orders`) ได้ภายในเวลาไม่เกิน 1 วินาทีในสภาวะปกติ

### 4.2 ความง่ายในการใช้งาน (Usability)
- **NFR-03 (Learnability):** พนักงานใหม่ต้องสามารถเรียนรู้และบันทึกออเดอร์แรกได้สำเร็จภายในเวลาไม่เกิน 3 นาทีโดยไม่ต้องเปิดคู่มือ
- **NFR-04 (Visibility & Consistency):** ตัวเลือกสาขา (Branch Selector) ต้องอยู่ในตำแหน่งมุมบนขวาเหมือนกันทุกหน้าจอ และสถานะของระบบต้องแสดงชัดเจนตลอดเวลา

### 4.3 ความถูกต้องและความปลอดภัย (Reliability & Security)
- **NFR-05 (Data Integrity):** ข้อมูลสต็อกสินค้าต้องสอดคล้องกับรายการขายเสมอ โดยการตัดสต็อกและการบันทึกออเดอร์ต้องได้รับการปกป้องจากปัญหา Race Condition ด้วย Database Transaction
- **NFR-06 (Authorization & IDOR Protection):** การแก้ไขข้อมูลสต็อกหรือการเรียกดูรายงานต้องระบุและตรวจสอบ `branch_id` เสมอ เพื่อป้องกันการเข้าถึงหรือแก้ไขข้อมูลข้ามสาขาโดยไม่ได้รับอนุญาต

## 5. ข้อจำกัดเชิงเทคนิคและสถาปัตยกรรม (Constraints)

1. **สถาปัตยกรรมระบบ:** พัฒนาในรูปแบบ Monolithic Architecture ด้วย Node.js และ Express ให้บริการ RESTful API และ Static Web Assets ที่พอร์ต `3000`
2. **ฐานข้อมูล:** ใช้ MySQL 8.0 ฐานข้อมูลเดี่ยวบน localhost จัดการข้อมูลหลายสาขาผ่านตารางเชิงสัมพันธ์และคอลัมน์ `branch_id`
3. **การออกแบบเชิงวัตถุ:** มี Domain Class `Order`, `OrderItem`, และ `MenuItem` ตามแบบแผน OOAD ของสัปดาห์ที่ 6 โดย `total_amount` ในคำสั่งซื้อต้องไม่ถูกจัดเก็บเป็นคอลัมน์ในตาราง แต่คำนวณผ่าน method `getSubtotal()` ตามหลัก 3NF
4. **เทคโนโลยีฝั่งผู้ใช้:** ใช้งานผ่าน Web Browser มาตรฐาน (Chrome, Edge, Safari, Firefox) รองรับการแสดงผล Responsive แบบ Desktop/Tablet สำหรับจุด POS

## 6. โครงสร้างฐานข้อมูลเชิงสัมพันธ์ (Database Schema)

ระบบอ้างอิง Schema จาก `wk07-schema.sql` และ ER Diagram ประกอบด้วย 7 ตารางหลัก:
1. `branch` (branch_id, name, address)
2. `category` (category_id, name)
3. `employee` (employee_id, branch_id, name, role)
4. `menu_item` (menu_id, branch_id, category_id, name, price, stock_quantity)
5. `orders` (order_id, branch_id, employee_id, payment_method, created_at)
6. `order_item` (order_item_id, order_id, menu_id, quantity, unit_price)
7. `stock_movement` (movement_id, menu_id, quantity_change, moved_at)
